# 面向 Agent 应用研发求职的模型能力演进方案

日期：2026-11-01。本文是设计与实施优先级提案，尚未实现其中的新模型设置、训练及部署功能。

## 已明确的目标

- 主投国内大厂日常实习、秋招的大模型应用 / Agent 研发岗位。
- 支持租用 GPU 训练，模型选择不受当前笔记本 6 GB 显存限制。
- 最终用户可选择自部署开源模型，或填写自己的云 API Key。
- 项目成果应有部署、数据、训练、评测和实际业务收益证据。

## 竞争力判断

| 改进 | 本项目的优先级 | 可展示的能力 |
| --- | --- | --- |
| 自部署 / BYOK 双模式及凭据隔离 | P0 | 模型服务抽象、配置隔离、真实产品交付 |
| 可复现的质量、延迟、吞吐与成本评测 | P0 | 实验设计、性能优化、效果归因 |
| 对证据遵循、澄清和回复行为做 SFT | P1 | 业务问题到数据、训练、上线的闭环 |
| 真实模型动作与受控执行反馈 | P1 / 后续范围 | 受约束的 Agent 规划和执行 |
| 有可验证奖励的 GRPO 对照实验 | P2 | 奖励设计、训练稳定性与收益分析 |
| 单纯扩大模型或追加训练术语 | 低 | 单独不能证明工程或算法收益 |

这是结合岗位描述与项目现状的判断，不是录用保证。
参考：[华为云 Agent / 推理实习岗位](https://www.huaweicloud.com/lab/algorithm/intern_recruitment.html)、[百度千帆 Agentic RL / 推理优化实习岗位](https://talent.baidu.com/jobs/detail/INTERN/52415af4-405a-4f07-8392-d4b63e76df8c)。

## 产品边界

### 自部署模式

自部署包括用户电脑、用户自己的服务器或私有网络中的推理服务。
正式服务优先提供 vLLM 的 OpenAI-compatible 接口；Ollama 可作为个人体验入口。
同一模型实例可承载多个角色，通过各角色的 system prompt 与推理参数区分；不要求为五个 Agent 各训练一套权重。

全本地模式必须覆盖实际运行中的生成、理解、风险评估、正文审核、查询改写、记忆摘要和 embedding，不隐式依赖云端 Key。
离线评测模型另行配置，不与线上运行模式混淆。

### 用户自填 API Key 模式

用户选择供应商、模型并填写 Key，经过连接和能力测试后保存。
聊天与 embedding 分开配置；一个供应商不提供 embedding 时，允许明确选择本地 embedding 或另一供应商。
先支持有限的经过验证的供应商；高级自定义地址由部署管理员控制。

集中托管的网站不能直接将访问者电脑的 localhost 当成后端可访问地址。
第一版自部署体验以整套应用运行在用户自己控制的环境为准；托管应用连接远端自部署服务时需要明确可达的服务地址。

## 核心架构

当前 get_settings() 为缓存的全局 .env 配置，AgentModelRegistry 只覆盖角色 provider / model。
它可保留为部署默认值，但不能承担多用户凭据和模型选择。

建议引入：

- ModelConnection：连接所有者、部署/账号作用域、协议、服务地址、凭据引用、能力检测结果。
- CredentialStore：服务器端加密保存 Key，提供撤销、替换和权限检查；接口只返回掩码。
- ModelProfile：生成与 embedding 连接、角色绑定、采样、上下文和并发预算。
- ModelGateway：统一推理调用、流式适配、错误归类、超时、重试与观测。
- ModelArtifact：基座 revision、adapter、数据集哈希、chat template、量化方式、评测报告。
- RequestModelSnapshot：每轮解析出不可变配置，记录 revision，避免全局变量修改导致串用 Key 或中途换模型。

凭据不写入 trace、工具任务、日志或前端持久化存储；缓存不得跨越凭据所有者错误复用。
失败切换到其他供应商须服从用户明确选择的策略；全本地模式不自动切到云端。

能力检测至少覆盖非流式、流式、JSON、上下文限制和 thinking 输出兼容性，不能只凭 /models 成功就标记服务可用。

## 向量库管理

聊天模型变更通常无需重建知识库。
embedding 模型变更会改变向量空间，即使维度相同也不能直接复用旧向量。
索引绑定知识库作用域、语料版本、embedding 连接/模型版本、维度与切块配置。
新索引构建并验收后再切换，运行中的请求继续使用自己的索引版本。
公共内置语料与用户私有知识库需要明确隔离。

## 训练路线

首个正式基座候选为 Qwen3-8B，先完成未训练基线；更大模型在相同任务与预算口径下再比较。
模型与推理配置须固定 revision，先做显存与吞吐试运行，再确定租用资源。
参考：[Qwen3-8B 模型卡](https://huggingface.co/Qwen/Qwen3-8B)。

### SFT

主要目标：提升咨询回复的证据遵循、证据不足时的澄清/有限回答、表达边界和指令遵循。
路由模型 SFT 可作为辅助实验，但不把三分类训练作为整个项目后训练能力的唯一证据。
动态校园资源继续通过 RAG 获取，训练学习如何使用和约束证据。

数据保留来源、许可/授权、场景 family、生成模型、人工审核状态和版本哈希。
合成或获授权的数据才进入训练导出；业务 trace 不自动成为训练集。
训练、验证、测试按 family 去重隔离；另建未用于调参的测试集，现有公开开发场景不能充当全新盲测。

### GRPO

先判断 SFT 后还存在什么可优化的错误，再选择 GRPO 任务。
可研究证据约束回答、证据不足的澄清决策，或后续新增的多步检索动作策略。
奖励包含任务达成、可核验事实、来源支持、边界违反与执行成本；需检查奖励投机和同组奖励无差异比例。
自然语言事实支持不能仅靠出现引用编号判定，需独立证据检查、模型评审与人工抽检。

当前工具任务由服务端风险策略选择，不能把它描述成模型已自主学会 Function Calling。
如宣称 Agentic RL，需要新增并实际验证模型动作、环境反馈、多步轨迹与训练闭环；工具授权、安全覆盖和最终执行仍由服务端控制。

参考：[TRL SFT](https://huggingface.co/docs/trl/sft_trainer)、[TRL GRPO](https://huggingface.co/docs/trl/grpo_trainer)。

## 实验验收

同一基座至少比较：原始模型、仅提示词改进、SFT、SFT + GRPO；DeepSeek 作为独立参考组。
固定工具能力、RAG 语料、输入上下文、预算、解码和评审口径，区分模型提升与编排提升。

记录完整契约完成率、证据支持率、恰当澄清/拒绝率、风险边界、工具执行与幂等结果、回退率、最终审核完成延迟、并发吞吐、显存及真实 usage。
线上 SSE 在审核后发送，首个可见块延迟与底层模型 TTFT 分开报告。
自部署成本包含 GPU 租用、运行时长、利用率与吞吐，不能因为没有 API 账单就记为零成本。
GRPO 的训练奖励增长不能替代未见测试集上的业务收益；失败、退化和无收益结果保留。

## 建议实施顺序

以新增的 [综合提升实施计划](IMPROVEMENT-ROADMAP.md) 为执行顺序与阶段验收依据：

1. 保留现有可运行基线，优先补 ModelGateway、token/费用账本与缓存指标。
2. 建立质量、延迟、吞吐与成本基准，定位实际瓶颈。
3. 完成 ModelConnection / Profile、BYOK 隔离和自部署双模式，接入未训练模型基线。
4. 针对瓶颈做性能/成本优化，验证效果与安全边界。
5. 构建版本化数据，训练并部署 SFT 模型，完成同基座对照。
6. 针对剩余错误做小规模 GRPO 试验，根据未见测试集收益决定是否扩大投入。
7. 每阶段同步整理复现实验、失败分析、演示和有真实数字的面试材料。
