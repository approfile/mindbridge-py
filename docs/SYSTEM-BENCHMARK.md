# 系统基准评测：质量、延迟、吞吐、费用与缓存

协议版本：`system-baseline-v1`。数据集版本：`system-baseline-v1-20261101`。
这是阶段 2 的工程基准，采用作者可见、AI 辅助编写的合成输入与规则，不是专家 gold、独立盲测或临床验证。

## 执行入口

运行时使用已有本地 Docker 栈。`.env` 继续提供模型配置；脚本不输出或归档密钥。需已启动 MySQL、Redis、Mailpit，且生成/embedding 配置可用。

先创建一个专用空白 MySQL 数据库 `mindbridge_bench_<本次名称>`，并仅为现有应用账号授权该库。脚本拒绝业务库名、非 MySQL、非空的初始数据库和已存在的输出目录；不会自动删库、清 Redis 或覆盖旧试次。

```powershell
# 把数据库名替换成自己预先创建并授权的独立空库。
docker compose -f docker-compose.local.yml exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e "CREATE DATABASE mindbridge_bench_example CHARACTER SET utf8mb4; GRANT ALL PRIVILEGES ON mindbridge_bench_example.* TO mindbridge;"'
docker compose -f docker-compose.local.yml exec -T app python scripts/run_system_benchmark.py --database mindbridge_bench_example --output target/system-benchmark/example
docker compose -f docker-compose.local.yml exec -T app python scripts/export_system_benchmark.py --input target/system-benchmark/example --output target/system-benchmark/example/audited-summary.json
```

`--smoke` 运行缩小后的两场景、单并发、单试次，以及两种编排的故障与容量探针。
`--mock` 用于离线接线验证，不产生真实模型质量结论。正式报告必须同时记录这两个标志，禁止拿 smoke/mock 成绩冒充完整基准。

每次运行创建独立进程，绑定容器内 `127.0.0.1:18081`，不映射新端口。正式 `8080` 服务保持原样。

## 冻结计划与分层

`app/benchmark/dataset-v1.json` 与其 `.sha256` 文件固定输入和契约，加载时校验内容哈希。模型调用前先写 `plan.json`，记录预定试次、源码/语料哈希、模型参数、环境版本和运行限制；执行后再次核对源码。随机种子固定为 20261101，只用于确定任务顺序，不声称能控制云模型随机性。

| 层 | 场景与试次 |
| --- | --- |
| nominal | 7 个场景：学习规划、编程、考试压力、短期睡眠困扰、明确当前风险、长历史事实、同会话重复请求；每种编排分别在 1/2/4 并发下重复 2 次 |
| context_intervention | 1 个明确缺资料的校园服务场景，受控返回空检索；同样运行 1/2/4 并发、2 次，不混入自然检索质量 |
| injected_fault | 首次生成尝试注入 503、所有生成尝试注入 503；每种编排各 1 次，不当作真实服务商故障发生率 |
| admission_probe | 每种编排用 5 个独立账号同时发请求，检查 4 轮准入及 1 个容量拒绝；拒绝不进入正常模型吞吐或任务质量分母 |

完整计划为 **110 个场景试次、122 次在线 HTTP 请求**：96 个固定场景试次含 108 个请求，4 个故障试次含 4 个请求，两个五请求容量批次。重复会话场景每个试次有两轮；这些不是 122 个独立问题。

长历史由 12 对合成用户/助手消息预先写入独立 SQL，合计 24 条，包含早期旧代号和末尾明确更正；读取与压缩走真实业务代码。预置历史不是 24 次真实模型调用。重复请求场景串行沿用同一会话。其余场景使用全新会话，不能复用其他用户的结果。

## 隔离与对照

- 独立 MySQL 数据库；账号、会话、报告、工具任务和 usage 账本都在该库。
- Redis db14，且使用 `mb-bench:<运行名>:<编排>` 的随机运行作用域；不会扫描或迁移业务 db0 的旧缓存。
- 独立 Chroma、快照、隐私密钥、Excel 台账和日志，均位于本次输出的 `private/`。
- SMTP 固定发送本机 Mailpit，使用 `.test` 收发人和唯一的 benchmark 邮件主题；不能解读为已联系真实人员。
- 文档 embedding 从当前公开内置语料真正生成；两种编排复用本次索引，费用记入 `knowledge_index`，不依赖历史私有 embedding 缓存。

对照复用 `app/evaluation/sequential.py` 的固定顺序工作流：理解→风险→按需上下文→回复计划→计划检查。模型角色、RAG、记忆、计划门槛、正文规则与模型审核、重试和预算一致。它是简化调度编排，**仍包含多个角色与多次模型调用**，不能称“一次单模型调用基线”。

对照由基准子进程注入，生产 factory 没有新增模式开关。当前按 event-driven 后 sequential 的顺序执行，有云端缓存、服务负载与顺序偏差，因此可以描述观测差异，不能仅凭本批数据断言因果收益。

## 指标定义

质量按场景试次计数，性能与费用按真实请求或 attempt 计数，两种单位分开。

| 指标 | 口径 |
| --- | --- |
| 任务契约 | 意图/风险、助手消息持久化、报告/工具策略、回复终态等机械约束，加独立 goal/safety，适用时再加 grounding/clarification；任一 fail 则失败，缺失判定为 unknown |
| 证据支持 | 独立离线评审实际可见回答和实际检索上下文；只在适用场景评分，不用运行时 Safety 的 approved 自证 |
| 澄清/有限回答 | 缺资料场景是否承认缺失、适当澄清/核对官方来源并拒绝编造或保证；与自然场景分开 |
| 回退率 | `safe_fallback轮次 / 该层HTTP请求数`；受控持续故障下正确兜底可满足故障契约，却不算正常生成完成 |
| 重试率 | 存在额外传输尝试的轮次 / 该层请求数；保留每次尝试和注入标记，不把修订当传输重试 |
| usage 覆盖 | 有有效供应商 usage 的 attempt / 记录的 attempt；完整轮次覆盖率另计，缺失值不填零 |
| 延迟 | 最近秩 P50/P95，附样本数；HTTP 整轮、模型正文首 token、服务端提交审核后首文本、客户端实际收到首文本分别统计 |
| 吞吐 | 整个并发批次中 SSE done 回复数 / 首个请求开始到最后请求结束的墙钟时间；同时给出所有 HTTP 完成数/s |
| 费用与缓存 | 沿用阶段 1 的 Decimal 标价估算、币种分账及各层缓存分母；记录已知费用的各角色占比和未知覆盖 |

请求异常、超时或回退仍进入相应层的统计，不只计算成功请求。无可见文本的首 token 为 null；P50/P95 只在有该测量的样本上计算，并显示样本数。容量拒绝的延迟单列，不能与正常生成混合后宣称变快。

吞吐属于单客户端闭环工作负载，客户端取证/落库等待可能影响下一请求的发起，**不是服务端最大容量**。批次整体指标在 `cohortPerformance`；nominal 与空检索干预的质量在 `groups` 中分别展示，不把不同证据层混成质量总分。

云端缓存仅采用服务商返回。`first_observed` 不代表完全冷缓存；同会话第二轮标签为 `same_session_repeat`。文档向量复用的单位是 chunk，Redis 历史的单位是主会话读取次数；RAG Recall 不能替代缓存命中率。

原始 `observationLabel` 表示计划中的首次/重复位置；如果第一轮失败且没有建立会话，第二轮不能视为实际热会话。导出审计按真实 session ID 校验，额外生成 `audited-turns.csv` 和按实际会话状态分组的缓存指标，将这种情况标为 `continuation_not_established`，不覆盖原始证据。

## 独立评审及成本分账

评审使用单独提示与调用，输入为实际合成用户消息、实际可见回答和实际检索内容，输出必须带回答中的连续引文。字段、引文或摘要绑定不合法则不能判 pass；最多两次格式尝试，全部保留。任一机械失败不能被模型评分覆盖，unknown 不从分母删除；存在 unknown 时给通过率上下界，拒绝伪造确定单点。

评审与生成使用当前同一供应商/模型配置，有同源偏差；尚无独立专家复核。不能把单次模型裁决说成客观准确率或临床安全率。

账本分别记录 `knowledge_index`、`online_chat`、`offline_judge`。训练数据生成本阶段没有运行，标为 `not_run`，不是“费用为零”。注入的 503 是本地受控响应，保留 `injectedFault`；它没有真实上游 usage，费用为未知，不伪造供应商账单或当作真实故障率。

正式运行目录：`target/system-benchmark/baseline-v1-20261101/`。

公开可审计提要：[system-baseline-v1-20261101.json](benchmarks/system-baseline-v1-20261101.json)。

110/110 场景试次、122/122 HTTP 请求全部记录，request ID 唯一；全部在线 attempt 与独立账本 CSV 对齐。源码哈希在采样、离线评审结束和导出时一致。另保留 `source-snapshot.zip`，只含已核对源码、公开语料与依赖清单，不含 `.env` 或密钥。完整回归为 **335 项测试、6 组 Harness**。

### 性能：包含失败请求的整批指标

下表每行是 18 个 HTTP 请求的闭环混合工作负载，包含 nominal 与空检索干预；**只合并性能，质量仍分层**。首可见文本指标只对实际收到文本的请求计算，四并发各只有 16 个样本，不能把失败前无文本的请求补成 0。

| 编排 | 并发 | SSE done / 请求 | HTTP P50 / P95（秒） | 客户端首文本 P50 / P95（秒） | done 回复 / 秒 |
| --- | ---: | ---: | --- | --- | ---: |
| event-driven | 1 | 15/18 | 3.775 / 18.341 | 3.743 / 18.308 | 0.151 |
| event-driven | 2 | 16/18 | 3.616 / 8.764 | 3.585 / 8.736 | 0.343 |
| event-driven | 4 | 14/18 | 3.568 / 14.833 | 4.370 / 14.791 | 0.544 |
| sequential | 1 | 15/18 | 3.390 / 14.189 | 3.364 / 14.162 | 0.154 |
| sequential | 2 | 14/18 | 3.600 / 13.586 | 3.573 / 13.556 | 0.271 |
| sequential | 4 | 13/18 | 3.636 / 14.117 | 3.617 / 14.089 | 0.387 |

底层模型流的首正文块 P50 约 **0.57–0.65 秒**，远低于用户首个已审核文本的等待时间。后续需要分析完整生成、正文审核和修订，而不是把低模型 TTFT 当成用户已经收到回答。

此处是同一台 Windows/Docker Desktop 上共享 MySQL/Redis 服务实例的独立数据库测试，没有硬件资源隔离，也没有随机交错两种编排的执行顺序。P95 的样本很少，不能据此宣称某个并发档位总是更快，或将本批差值当作调度架构的因果收益。

### 质量：失败与未知均保留

| 编排 / 自然场景并发 | 场景试次 | pass / fail / unknown | 契约通过率可核验范围 |
| --- | ---: | --- | --- |
| event-driven / 1 | 14 | 12 / 1 / 1 | 85.7%–92.9% |
| event-driven / 2 | 14 | 11 / 1 / 2 | 78.6%–92.9% |
| event-driven / 4 | 14 | 9 / 3 / 2 | 64.3%–78.6% |
| sequential / 1 | 14 | 13 / 1 / 0 | 92.9% |
| sequential / 2 | 14 | 10 / 2 / 2 | 71.4%–85.7% |
| sequential / 4 | 14 | 8 / 3 / 3 | 57.1%–78.6% |

这些范围仅来自 unknown 的上下界，**不是统计置信区间**。每行只有 7 种自然场景、各重复 2 次，不是 14 个独立问题。RISK 场景的契约包括回复、报告、工具执行与独立评分，不能把其契约通过率说成危险识别准确率。

空检索证据干预共 12 个试次：event-driven 2/6 契约通过，sequential 0/6。其余均进入通用兜底，修订预算耗尽；没有通过降低安全门槛或删除失败来补成绩。长历史事实场景两种编排各 6/6 通过，只覆盖这个固定的代号更正场景。

100 组离线评审使用 111 次真实 API 调用；90 组取得有效结构与正文引文，10 组两次均无有效裁决，另有 1 组第二次才有效。共 21 次无效尝试，费用全部保留。未知评分不算通过；本批不能作为专家质量结论，也不能说明评审器已经校准。

### 费用、覆盖率与缓存

| 分账 | 真实用量 / 费用估算 |
| --- | --- |
| 在线全部层，含故障/容量探针 | 438 次 attempt，其中 432 次真实上游请求、6 次明确标记的本地 503；已知 700,869 token；USD 0.053300028、CNY 0.0005180 |
| 独立离线评审 | 111 次调用、145,490 token；USD 0.025268079，包含无效评分 |
| 独立知识库建库 | 11 次调用、7,437 输入 token；CNY 0.0037185 |

真实上游请求均拿到有效 usage；记录的 attempt 总覆盖为 432/438，差额是本地注入的 503。SQL 死锁发生在模型工作前，相关用户请求没有模型账本，单列为 missing-ledger，不因此声称所有 HTTP 请求都有完整模型用量。四并发每种编排的完整账本请求比例为 16/18。

在 1/2/4 并发的固定场景工作负载中，event-driven 的已知 USD 费用约 **59.7%** 属于 SafetyAgent、**36.6%** 属于 ResponseAgent；sequential 分别约 **59.3% / 37.4%**。Safety 包含风险评估与正文审核，不能直接归结为“审核可以删除”。

| 缓存口径 | event-driven | sequential |
| --- | --- | --- |
| 固定场景的服务商前缀缓存，按有拆分输入 token 加权 | 66.7% | 74.1% |
| 所有已执行的主会话历史读取 | 5 hit / 47 miss | 6 hit / 46 miss |
| 实际成功延续的重复会话读取 | **5/5 hit** | **6/6 hit** |

### 故障、超限和真实副作用

- 两种编排的单次 503 重试、持续 503 安全兜底各一次，4 个受控契约均通过；只是定点故障验证，不是自然恢复率估计。
- 两个五并发容量批次均为 4 个请求获准、1 个 `TURN_CAPACITY_EXCEEDED` 拒绝。获准不等于成功回复：其中也发生了会话记忆死锁。
- 专用数据库中 47 份报告、71 个工具任务 SUCCESS；物理 Excel 对应 47 份报告各写一次；12 份高风险报告的邮件均在独立主题的本机 Mailpit 收件，不代表真人已介入。

### 瓶颈结论与后续优先级

1. **先修复并发持久化可靠性。** 全批共 10 次 `memory.synchronize` 错误码 1213：正常四并发 4 次、容量探针 6 次。它对应 MySQL 的 [ER_LOCK_DEADLOCK](https://dev.mysql.com/doc/mysql-errors/8.0/en/server-error-reference.html#error_er_lock_deadlock)。当前证据确认了错误与阶段，尚未取得锁等待图来证明具体哪条语句组合形成环；后续应单独复现事务锁序与新会话记忆创建，再用此冻结基准作修复前后对照。官方说明见 [InnoDB 死锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html)。
2. **提高缺资料时的有限回答完成率。** 当前空检索场景常耗尽修订预算后兜底；应区分资料不足的合理边界与真正无效回答，保持事实约束，不用放宽审核制造通过率。
3. **检查 Safety 上下文与重复工作。** 它占本批 USD 开销约六成，应先拆解风险评估、逐句证据审核及修订成本，再决定减少哪些冗余；不能靠取消必要审核降本。
4. **校准离线评审与扩大样本。** 当前有效裁决覆盖 90%，且同供应商、缺少专家复核；先分析无效裁决、完成人工抽检，再扩大场景或据此构造 SFT/奖励数据。

这次没有改变生产事务、安全规则、模型提示或缓存策略来改善数字。固定顺序对照与事件编排互有得失，证据不足以给多 Agent 宣称全面优势。阶段 2 完成的是可重复测量和问题定位，并不意味着业务质量已经达标。

前置 smoke 记录独立保留：首轮私有探针路由被根 StaticFiles 挂载遮蔽，尚未执行场景便退出；修复后 smoke2 完整执行 18 个试次。两者都不是正式成绩，没有用它们替换正式批次的失败结果。
